## Purpose

This document defines **how agents operate** within the BY-SYSTEMS platform. It is the contract between the human owner and any agent (Rune, subagents, future agents) working on the platform.

**If it's not in this file, it's not a rule. If it is in this file, it's non-negotiable.**

## 1. Session Protocol

### 1.1 Start of session

Every session, every agent, no exceptions:

```
1. Read SOUL.md               → who am I
2. Read USER.md               → who is the human
3. Read OPERATING-STANDARD.md → this file (the rules)
4. Read openclaw-status.md    → where are we now
5. Read MEMORY.md             → what do I remember
6. Read {repo}/CLAUDE.md      → repo-specific context (if working in a repo)
```

### 1.2 During session

- Track work with tasks (TodoWrite or equivalent)
- Update `openclaw-status.md` §8 (Completed actions log) after each significant action
- If a new risk/issue is found → RAID.md + GitHub Issue + Projects board (**all three, atomic**)
- If an architectural decision is made → ADR in the relevant repo

#### Scope discipline (mandatory)

- Execute ONLY work explicitly approved by @yboujraf
- Gap found during approved work → document in NEEDS.md, surface in Discord → **stop. Do not fix.**
- GitHub issues created ONLY for approved work — never speculatively
- Future feature requests / infra ideas → NEEDS.md only, never directly to GitHub Issues
- Running "ahead" without approval is a violation even when the work is correct

### 1.3 End of session

Before ending any session:

```
1. Archive openclaw-status.md with timestamp (cp to archive/openclaw-status-{ISO-timestamp}.md)
2. Update openclaw-status.md:
   - §Update History (who, when, what)
   - §Pending actions (handoff queue for next session)
   - §Completed actions log (what was done)
3. Update MEMORY.md if any new standing rules, decisions, or truths
4. Commit changes to relevant repos (do NOT leave uncommitted work)
```

**Rule:** The next agent must be able to resume from `openclaw-status.md` alone, without asking "what happened?"

## 2. Status File Convention

### 2.1 `openclaw-status.md` — the live tracker

- Always at workspace root: `/home/by-systems/.openclaw/workspace/openclaw-status.md`
- Always the current, up-to-date version
- Has an Update History table at the top with: timestamp (UTC), updated by, summary

### 2.2 Archiving

Before any major update:
```bash
cp openclaw-status.md archive/openclaw-status-YYYY-MM-DDTHHNN.md
```

Example: `openclaw-status-2026-03-30T1900.md`

Archives are immutable snapshots. Never modify an archived file.

### 2.3 Required sections

Every `openclaw-status.md` must have:

| Section | What it tracks |
|---|---|
| Update History | Who updated, when, what changed |
| CI Health | Per-repo CI status (green/red) |
| Audit Status | What's been verified, what's pending |
| Cross-repo File Matrix | What exists where (living checklist) |
| Secrets Redaction Status | What's redacted, what needs rotation |
| Pending Actions | Handoff queue — requires decision or approval |
| Completed Actions Log | Timestamped record of what was done |

## 4. Commit & Version Discipline

### 4.1 Conventional Commits — mandatory

```
type(scope): description

[optional body]
[optional footer: BREAKING CHANGE: ...]
```

| Type | Bump | When |
|---|---|---|
| `fix:` | patch | Bug fixes |
| `feat:` | minor | New features |
| `feat!:` / `BREAKING CHANGE:` | major | Breaking changes |
| `docs:` `test:` `chore:` `refactor:` `ci:` `perf:` `security:` | none | Non-functional |

### 4.2 Release flow

```
conventional commit → push → Release Please PR → review → merge → tag + release
```

**Never:** manually edit versions, manually run `cz bump`, skip Release Please.

### 4.3 Branch naming

```
{type}/{issue-id}-{short-description}
```

### 4.4 Pull Request Content Standard

Every PR description must include the following sections. Sections marked (if applicable) may be omitted when not relevant to the change.

**Workflow rules** — see `docs/adr/git/0001-workflow` (branching, merge strategy, protected branch, agent boundary).

#### 1. Summary (mandatory)

One paragraph: what changed and why. `Closes #NN` where applicable.

#### 2. Type (mandatory)

Checkbox matching the Conventional Commit type: `feat` / `fix` / `docs` / `chore` / `refactor` / `test` / `ci` / `security`.

#### 3. Files changed table (mandatory)

| File | Type | Change |
|------|------|--------|
| `path/to/file.py` | new / fix / update / delete | One-line description |

#### 4. Test results table (if code changed)

| Suite | Scope | File | Passed | Failed |
|-------|-------|------|--------|--------|
| Unit | ManagerName | `tests/unit/test_manager.py` | 16 | 0 |
| Integration | Domain | `tests/integration/test_lifecycle.py` | 14 | 0 |
| **Full suite** | **All** | `tests/` | **226** | **0** |
| Lint | ruff / ansible-lint / terraform fmt | `src/` + `tests/` | clean | — |

#### 5. Endpoints / resources covered (if API/infra code)

For `lib-*` repos:

| Endpoint | Method | Tested |
|----------|--------|--------|
| `/api/domain/action` | POST | unit + integration |

For `infra-terraform-*` repos:

| Module / Resource | Action | Tested |
|------------------|--------|--------|
| `module/vm-opnsense` | plan + apply | yes |

#### 6. Safety boundaries (if touching live systems)

- **READ-ONLY:** what must NOT be modified on the live device
- **CRUD safe:** what can be created/deleted with `inttest-` prefix
- **DISABLED only:** what must be created in disabled state

#### 7. How to review (mandatory)

Numbered steps guiding the reviewer through the change:

1. Read X — verify Y
2. Check Z — confirm W

#### 8. Checklist (mandatory)

Quality, security, docs checkboxes (per-repo `.github/PULL_REQUEST_TEMPLATE.md`).

#### 9. Review approval

- [ ] @yboujraf approved

Agents never check this box. @yboujraf is sole merge authority (see `docs/adr/git/0001-workflow §Agent boundary`).

## 5. Quality Gates

### 5.1 Definition of Done — nothing ships at 60%

Every deliverable, every repo:

- [ ] All public methods have docstrings
- [ ] ensure() / idempotent pattern where applicable
- [ ] dry_run=True on all destructive methods
- [ ] Unit tests — happy path + error codes
- [ ] Linting clean (ruff, ansible-lint, terraform fmt — per repo)
- [ ] Type checking clean where applicable (mypy)
- [ ] CHANGELOG entry
- [ ] CLAUDE.md + AGENTS.md updated if state changed
- [ ] RAID.md updated if new risk/issue found

### 5.2 Return dict contract (all Python libs)

All public methods that mutate state return `{"changed": bool, "action": str}`. No exceptions. See lib-synology-dsm ADR-0007.

<!-- TODO: update when v2 ships — Python libs will return EnsureResult dataclass. .to_dict() produces {"changed": bool, "action": str} for Ansible compatibility. -->

### 5.3 Idempotency — mandatory

Every automation action is safe to run repeatedly:
- `ensure()` pattern: fetch → diff → act only if different → return `{changed, action}`
- Running apply twice = same result as once
- `dry_run=True` previews without mutations
- Check before create, check before delete

### 5.5 CI Workflow changes — Opus review + @yboujraf approval required

Any change to `.github/workflows/` requires:

1. Opus review before commit
2. @yboujraf approval — no exceptions

CI workflow = platform gate. Same weight as an ADR. Zero tolerance for unilateral changes.

### 5.4 Test-first discipline

- Test fails → open issue first, then fix, then close with commit ref
- Issue closed = CI green + specific test covers the fix
- Never fix silently — issue first

> **Compliance:** ISO A.14.2.1 — Secure development policy

## 6. Security & Hardening

### 6.1 Secrets

> **MANDATORY READING before touching any credential:**
> 1. This section (the rules)
> 2. `workspace/infra/secrets/README.md` (the structure + Vault migration map)
> 3. `lib-synology-dsm/docs/adr/0009-secrets-json-schema.md` (the decision — why this format)

- **Never** commit credentials, tokens, passwords, private keys
- Redaction format: `<REDACTED:{type}>` — types: `password`, `token`, `ssh-pubkey`, `ssh-privkey`, `secret`, `ip-range`
- Pre-commit hooks: `detect-secrets` on every repo

**Credential storage:**

| Location | Format | Purpose | Who writes |
|---|---|---|---|
| `workspace/infra/secrets/*.json` | Vault KV v2 JSON | **Master store** — one file per credential | @yboujraf only |
| `{repo}/.env` | Flat key=value | **Consumer** — local runtime for tests/scripts (gitignored) | Developer (manual) |
| HashiCorp Vault (Phase 2) | KV v2 | **Target** — replaces JSON files when deployed | Vault admin |

**Rules for agents:**
- **Read** credentials from environment variables (`os.environ`, `python-dotenv`), never from JSON directly
- **Never** paste credential values in chat, docs, memory, CHANGELOG, or committed files
- **Never** hardcode credentials in scripts — use `source .env` or `dotenv` loading
- If you find a plaintext password in any file → redact immediately with `<REDACTED:{type}>` and flag in RAID.md
- `workspace/infra/secrets/` is not git-tracked — it lives on the Rune VM only

> **Compliance:** ISO A.9.4.3 — Password management; ISO A.10.1.1 — Cryptographic controls policy; NIS2 Art.21(2)(e) — Security in network/information systems

### 6.2 SSH

- Port 22222 (never 22) — per ansible-platform ADR-0001
- Key-only auth (Ed25519)
- Break-glass: password auth for `break-glass` group from OOB/MGMT only
- sshd_config fully replaced, not patched — per ansible-platform ADR-0002

> **Compliance:** ISO A.9.4.2 — Secure log-on procedures; ISO A.9.4.4 — Use of privileged utility programs

### 6.3 TLS

- `verify_ssl=False` is the **intentional platform default** — no infra for self-signed or LE certs yet. Decided 2026-03-30.
- Revisit when step-ca (Layer 2) is deployed and platform cert strategy is in place.
- Do NOT change `verify_ssl` default without owner approval.

> **Compliance:** ISO A.10.1.1 — Cryptographic controls policy; ISO A.13.2.1 — Information transfer policies

### 6.4 Compliance targets

- ISO 27001
- NIS1 / NIS2
- DORA
- GDPR

Phase 3 covers observability + security + compliance tooling.

> **Compliance:** ISO A.18.1.1 — Identification of applicable legislation

### 6.5 Naming & Identity Convention

> **Binding reference:** `doc-platform-core/docs/adr/0010-naming-and-identity-convention.md`
> **Environment tiers:** `doc-platform-core/docs/adr/0012-environment-tier-standard.md`

#### Environment tiers — always explicit

Six tiers, ordered pipeline: `poc → dev → test → staging → acc → prod`

**Rule:** `prod` is always explicit. No label = non-compliant, not "it's prod."

Every resource, credential, hostname, and service account must carry its environment tier label.

#### Account naming

| Account type | Pattern | Example |
|---|---|---|
| Human (standard) | `{handle}` | `yboujraf` |
| Human (admin) | `adm_{handle}` | `adm_yboujraf` |
| Service (per-env) | `svc-{function}-{env}` | `svc-terraform-poc` |
| Temporary (per-env) | `tmp-{purpose}-{env}` | `tmp-migration-poc` |

**`adm_` uses underscore** — POSIX compatibility exception. All other naming uses hyphens.

#### Key rules

- **`prod` label always explicit** — unlabeled resources are non-compliant
- **`adm_` prefix for admin accounts** — underscore for POSIX compatibility (LDAP/PAM sync)
- **`svc-{function}-{env}` for service accounts** — separate credentials per environment
- **Never use `adm_*` for daily work** — never use standard account for admin tasks
- **Groups follow `grp-{env}-{role}`** — RBAC by environment
- **`grp-prod-admin` max 2-3 members** — if more needed, review architecture

#### Compliance controls

- ISO A.9.1.1 (access control policy), A.9.2.1 (user registration), A.9.2.3 (privileged access), A.12.1.4 (env separation)
- NIS2 Art.21(2)(a) (risk management), Art.21(2)(i) (HR security)
- GDPR Art.32 (security of processing)

> **Compliance:** ISO A.9.1.1 — Access control policy; ISO A.9.2.3 — Privileged access management; ISO A.12.1.4 — Separation of environments; NIS2 Art.21(2)(a) — Risk management; NIS2 Art.21(2)(i) — HR security; GDPR Art.32 — Security of processing

## 7. Issue & Project Tracking

### 7.1 RAID atomic rule

Every issue, risk, or dependency triggers **three simultaneous actions:**

1. Entry in RAID.md (repo-scoped or platform-wide)
2. GitHub Issue with appropriate labels
3. GitHub Projects board entry (auto via `project-board-sync.yml`)

**All three. Same action. No exceptions.**

### 7.2 Issue lifecycle

```
Detected → RAID + Issue + Board → Assigned → In progress → Fix + test → PR → Review → Merge → Verify CI green → Close with commit ref
```

**Close manually after verification.** Never auto-close without confirming CI green and test coverage.

### 7.3 Labels

- `raid:risk`, `raid:action`, `raid:issue`, `raid:dependency`
- `phase:N` (0–5)
- `priority:high`, `priority:medium`, `priority:low`
- `bug`, `enhancement`

> **Compliance:** ISO A.12.1.1 — Documented operating procedures; ISO A.16.1.2 — Reporting information security events

## 8. Architecture Principles

### 8.1 Separation of concerns

- One repo = one concern (per ADR-0002)
- One language per repo (per lib-synology-dsm ADR-0005)
- One file owns each topic (see §3.2)
- Agent files: CLAUDE.md = tactical, AGENTS.md = strategic, CONTRIBUTING.md = operational

### 8.2 Design patterns

- **ensure() pattern**: fetch-diff-noop for all resource managers
- **Return dict contract**: `{"changed": bool, "action": str}` on all mutations
- **Credential provider hierarchy**: Vault > env > explicit
- **Dry-run gate**: every destructive action supports `dry_run=True`

### 8.3 Layer model (ADR-0006)

```
Layer 0 — Standards & Templates
Layer 1 — Proxmox Base
Layer 2 — Vault
Layer 3 — Identity
Layer 4 — Storage
Layer 5 — PoC Services
```

**Rule #1:** Nothing proceeds to next layer until current layer is documented, tested, signed off.
**Exception:** Libraries (Layer 4) can be developed in parallel with infrastructure layers.

## 9. Documentation Standard

### 9.1 Archive, never delete

Historical docs move to `docs/archive/`. Never delete documentation files.

### 9.2 ADR discipline

- Every architectural decision gets an ADR
- ADRs are immutable — supersede, don't edit
- **When to write an ADR:** if violating the decision would break the architecture or require a migration to fix

## 10. Methodology

### 10.1 Framework

BY-SYSTEMS operates with a hybrid approach:
- **ITIL** for service management (incident, change, problem management)
- **Agile/Scrum** for development sprints
- **DevOps** for CI/CD, IaC, and automation
- **RAID** for risk management

### 10.2 Sprint cadence

- Work is organized by platform layers (ADR-0006), not time-boxed sprints
- Each layer has exit criteria (documented in roadmap.md)
- Progress tracked in `openclaw-status.md` and `doc-platform-core/docs/status.md`

### 10.3 Roles

| Role | Who | Responsibility |
|---|---|---|
| Owner | @yboujraf | Decisions, approvals, direction |
| Agent (Rune) | AI agent | Implementation, documentation, tracking |
| Subagents | AI agents (spawned) | Parallel tasks, research, execution |

#### Scope boundary (Rune-specific)

Rune does not extend scope. Ever.

If Rune identifies work outside the approved task:

- Write it to NEEDS.md
- Surface it in Discord with context
- Wait for approval

Running "ahead" without approval is a violation even when the work is correct.

### 10.4 Communication

- Discord `#bot-openclaw`: primary agent-to-owner channel
- GitHub Issues: formal tracking
- GitHub Projects board: visual progress
- `openclaw-status.md`: session-to-session handoff
